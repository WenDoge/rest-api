# Взлетаем к заветному офферу

## Предусловие

1. Прочитать документацию по Go и используемым библиотекам, конкретные пункты:

   - Go
     - Go Modules
     - `context`
   - Gin
     - Getting Started
     - Routing
     - Middleware
     - Model binding and validation
   - Конфигурация приложения и переменные окружения
   - База данных
     - подключение к PostgreSQL через `pgx`
     - CRUD на голом SQL
     - миграции схемы: `pressly/goose` или `golang-migrate`
   - Аутентификация
     - `golang-jwt/jwt/v5`: создание токена, валидация, работа с claims
     - хэширование пароля: `golang.org/x/crypto/bcrypt`

2. Делать последующие задания `без использования нейронных сетей`. Это значит, что их можно использовать для получения знаний о той или иной вещи, но не проси написать весь код за тебя. Задавай вопросы по типу: “что это за технология? для чего используется? какие настройки нужно передавать в данный метод?”. И `максимально` рекомендую на первых шагах постоянно спрашивать “откуда ты взял данную инфу?”. Так ты сможешь с уверенностью понимать, что нейронка не предлагает тебе фигню и можешь обратиться к первоначальному источнику.

3. Обязательно использовать при реализации обращений в БДшку паттерн Repository.

4. После прочтения документации можно чекнуть, как выглядит примерная структура проекта на Go: именование папок, что в них лежит и т.д. Для этого можно посмотреть официальную документацию Go **Organizing a Go module**.

## **🚀 Цель**

Целью задачи является реализация REST API на Go. Сервис должен позволять работать с пользователем (CRUD):

1. регистрация
2. получение профилей и профиля
3. обновление профиля
4. удаление профиля
5. вход в систему

## **✍️ Задание**

Необходимо инициализировать проект на Go с использованием Gin и СУБД PostgreSQL, которую потребуется поднять в docker-compose (или docker). Кстати, в docker-compose поднимается только БД, а Go-приложение запускается в терминале.

> 🤓 Ниже будут описаны уровни разной сложности. Твоя цель выполнить каждый из них перед отправкой на ревью.
> Если понимаешь, что ты в полном блоке — обращайся за подсказкой, но помни, что наша задача научиться работать самим.

### **1 уровень**

Должен быть работающий проект на Go и подключение к PostgreSQL (обязательная СУБД поднята в docker compose / docker).

Схему таблиц заводи миграцией: проект должен подниматься с нуля одной командой.

На этом уровне нужно реализовать регистрацию пользователя. В запросе на регистрацию пользователь должен передать следующие поля:

- логин
- email
- пароль
- возраст
- описание о себе (до 1000 символов)

После регистрации пользователю должен выдаваться `access_token` и `refresh_token`. Как реализовать JWT-токены на Go можно найти в документации `golang-jwt/jwt` или на YouTube. Если срок access токена истёк — должна вылетать ошибка 401 и пользователь должен получить новый токен с помощью refresh токена.

Refresh-токен должен храниться в базе, а не только жить на клиенте. Иначе его невозможно отозвать: при утечке он работает до конца срока, и сделать с этим нельзя ничего. При обновлении пары старый refresh гасится, а на его место выдаётся новый — это называется ротацией.

Кроме регистрации пользователь может залогиниться по логину и паролю (пройти аутентификацию и авторизацию). В аутентификацию входит выдача новых токенов **😎**

Также пользователь должен иметь возможность получить информацию о себе (о своем пользователе): все поля. В роуте получения информации о себе не должно быть параметра `:id`. Должно быть, например, так `/profile/my`, а не `/profile/:id` (где `:id` — это айди пользователя).

Ещё одно требование, сквозное для всей домашки: `context` запроса прокидывается через все слои до самого запроса в базу — `QueryContext`, `ExecContext` или методы `pgx`, принимающие `ctx`. Если клиент отвалился или сработал таймаут, запрос в Postgres должен отмениться, а не доработать впустую. Репозиторий, который первым аргументом не принимает `ctx`, в Go считается написанным неправильно.

### **2 уровень**

Реализовать функциональную возможность получения всех пользователей для авторизованных юзеров. Предусмотреть пагинацию и фильтр поиска по логину.

### **3 уровень**

Дополнить логику обновлением и удалением пользователя. Удаление пользователя должно быть мягким (Soft-delete).

### **😎 4 уровень — гигачад**

Описать Swagger документацию и покрыть тестами.

Для Swagger можно использовать `swaggo/swag` + `swaggo/gin-swagger`.

- Если интересно разобраться в теме интеграционных тестов, можно изучить `testcontainers-go`. Но внедрять в домашке необязательно.

## **🟢 Критерии приемлемости**

1. Проект необходимо залить в свой публичный git репозиторий и скинуть ссылку на проверку
2. Должен быть открытый PR направленный в main — так мы сможем оставлять комментарии
3. Проект должен запускаться: поднял docker-compose, накатил миграции, запустил приложение — и оно работает
4. Приложение должно корректно завершаться по Ctrl+C: сервер перестаёт принимать новые соединения, активные запросы дорабатывают, пул соединений с базой закрывается. В Go это делается руками и часто спрашивается на собеседованиях

## **🪄 Дополнительная информация**

Каждый уровень в задании описан намеренно без подробностей. Кстати, иногда так делают в рабочих задачах.

С твоей стороны требуется показать максимум своих знаний и стараний — каждая инициатива будет высоко оценена. Например, в первом уровне можно хранить пароль в виде хэша. А для механизма авторизации использовать JWT.

Прояви энтузиазм к выполнению задания 🤙 Так ты прокачаешься в своих скиллах и мы с тобой быстрее найдем заветный оффер.
